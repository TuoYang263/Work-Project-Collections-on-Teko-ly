# M8 - dbt Metadata Refresh and Pipeline Monitoring Layer

## Purpose

M8 introduces an ADE-inspired metadata refresh layer for the Olist E-Commerce Analytics & Pipeline Monitoring Portal.

The goal is to parse dbt artifacts generated by each scheduled pipeline execution and load structured metadata into BigQuery monitoring tables. These tables preserve append-only historical records of pipeline runs, model executions, test results, model metadata, column metadata, and lineage relationships.

This layer helps the project move from a working analytics pipeline to a monitorable and auditable data platform foundation.

---

## Scope

M8 focuses only on dbt artifact-based metadata refresh and pipeline monitoring.

In scope:

- Parse `manifest.json`
- Parse `run_results.json`
- Parse `catalog.json`
- Create BigQuery dataset `olist_monitoring`
- Create append-only monitoring tables
- Store historical pipeline run records
- Store model run status and runtime history
- Store dbt test result history
- Store model metadata snapshots
- Store model column metadata snapshots
- Store lineage dependency edges
- Support SQL-based monitoring analysis

M8 should support future analysis such as:

- Current run vs previous run
- Current run vs recent average
- Model row count changes
- Test result history
- Model status history
- Runtime changes
- Failed test tracking
- Lineage impact analysis foundation

---

## Out of Scope

M8 does not include:

- AI assistant
- M9 implementation
- React portal
- Power BI dashboard
- Airflow, Composer, Dagster, or Prefect
- Full ADE implementation
- DataHub or OpenLineage integration
- Alerting system
- Slack or email notifications
- Root cause automation
- Governance UI

M8 should remain a small, controlled metadata monitoring layer based on dbt artifacts and BigQuery.

---

## Source Artifacts

M8 uses the following dbt artifacts:

| Artifact | Main Usage |
|---|---|
| `manifest.json` | dbt project structure, models, tests, sources, dependencies, descriptions, columns, configs |
| `run_results.json` | execution status, runtime, failures, adapter responses, invocation metadata |
| `catalog.json` | relation metadata, column data types, row counts, table size metadata where available |

---

## Target BigQuery Dataset

The monitoring dataset is:

```text
olist_monitoring
```

This dataset stores historical metadata generated from each pipeline run.

The tables are append-only. Each pipeline execution should add new records rather than overwrite previous records.

---

## Recommended Monitoring Tables

### 1. `pipeline_runs`

Grain: one row per dbt pipeline execution.

Purpose:

- Track each dbt invocation
- Store overall run status
- Store run duration
- Store total model and test counts
- Support current run vs previous run analysis

---

### 2. `model_run_results`

Grain: one row per dbt model execution per pipeline run.

Purpose:

- Track model execution status
- Track model runtime history
- Identify failed or slow models
- Support model status history and runtime trend analysis

---

### 3. `test_run_results`

Grain: one row per dbt test execution per pipeline run.

Purpose:

- Track dbt test pass, fail, warn, and error results
- Store failed test information
- Support failed test tracking and test history analysis

---

### 4. `model_metadata_snapshots`

Grain: one row per dbt model per pipeline run.

Purpose:

- Store model-level metadata snapshots
- Store materialization, schema, alias, description, tags, and file path
- Store row count and table size metadata where available
- Support model row count change analysis

---

### 5. `model_column_snapshots`

Grain: one row per model column per pipeline run.

Purpose:

- Store column-level metadata snapshots
- Store column names, data types, descriptions, and parent model references
- Support documentation coverage and future impact analysis

---

### 6. `model_lineage_edges`

Grain: one row per dependency edge per pipeline run.

Purpose:

- Store upstream and downstream dbt dependencies
- Preserve source-to-staging-to-marts lineage
- Provide the foundation for downstream impact analysis

---

## Design Principles

M8 follows these principles:

1. Keep the layer append-only.
2. Preserve run history instead of only storing the latest state.
3. Keep parser logic separate from BigQuery loading logic.
4. Allow missing artifact fields without failing the entire metadata load.
5. Avoid adding orchestration tools beyond the existing Cloud Run Job and Cloud Scheduler setup.
6. Keep the implementation simple enough to explain in interviews and portfolio documentation.

2. Create BigQuery dataset `olist_monitoring`.
3. Create monitoring tables.

5. Build BigQuery append loader.

7. Update `run_dbt_job.sh` to run metadata refresh after dbt build.
8. Validate Cloud Run Job execution.
9. Add sample monitoring SQL queries.
10. Update README and architecture documentation.

## M8 Completion Criteria

M8 is considered complete when:

- `olist_monitoring` dataset exists in BigQuery.
- Monitoring tables are created.
- Each Cloud Run Job execution appends new monitoring records.
- Pipeline run history can be queried.
- Model run status and runtime history can be queried.
- dbt test result history can be queried.
- Model metadata and row count snapshots can be queried.
- Lineage edges can be queried.
- README and metadata refresh documentation are updated.
